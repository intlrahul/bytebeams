# Architecture Decision Records

Use an ADR for a durable decision that changes boundaries, data ownership, algorithms, dependencies, platform support, persistence, contracts, or delivery policy.

Number records sequentially: `NNNN-short-title.md`. Accepted ADRs are immutable except for corrections; supersede them with a new record. Link related implementation and documentation.

Before accepting an ADR:

1. State the context and concrete problem.
2. List viable options and consequences.
3. Record the approved decision without hiding uncertainty.
4. Define migration, testing, and rollback implications.
5. Obtain developer approval during planning.

The current conversation decisions are captured in normative documentation. Create individual ADRs as implementation makes their concrete schema/tool consequences real.
